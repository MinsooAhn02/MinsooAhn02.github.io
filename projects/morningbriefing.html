하루에 보는 정보들을 한곳에A place for the things I check during the day

일정은 달력에서, 날씨는 다른 화면에서, 관심 있는 소식은 검색으로 찾아보게 되잖아요. 이 정보들을 한 화면에서 보고 하루의 맥락까지 정리할 수 있으면 좋겠다는 아이디어를 냈어요. 그렇게 팀원 두 명과 MorningBriefing.AI를 만들기 시작했어요. 웹으로 열어볼 수 있고, Chrome 새 탭에서도 접근할 수 있게 한 개인 대시보드예요.

단순히 정보를 나란히 배치하는 데서 끝내고 싶지는 않았어요. 일정과 관심사, 그날 남긴 기록을 브리핑과 일기 흐름에 연결했어요. 그래도 사용자가 모든 기능을 똑같이 쓸 필요는 없어서 위젯을 켜고 끄고 배치를 바꿀 수 있게 했고, 한국어와 영어로 사용할 수 있게 만들었어요.

Schedules, weather, and the news I care about usually live in different places. I proposed putting them together in one screen and using that context to help make sense of the day. Two teammates and I turned that idea into MorningBriefing.AI, a personal dashboard available as a web app and through a Chrome new-tab extension.

We connected the information to a briefing and diary workflow as well as displaying it. A user's calendar, interests, and notes could contribute to that flow. People don't all need the same dashboard, so we made widgets configurable and supported both Korean and English.

사용자가 실제로 따라가는 흐름From opening the app to recording the day

로그인한 사용자는 온보딩에서 관심사와 설정을 정하고, 연결한 Google 권한에 따라 캘린더와 할 일 같은 개인 정보를 불러와요. 대시보드에서는 브리핑, 달력, 날씨와 관심 정보가 위젯으로 나뉘어 보여요. 날짜를 선택하면 해당 날짜의 일정과 기록을 살펴볼 수 있고, 설정에서 보이는 위젯과 순서도 조정할 수 있어요.

하루 동안 남긴 메모와 질문에 대한 답변은 일기 흐름으로 이어져요. AI가 정리한 내용을 보고 사용자가 다시 고칠 수 있게 했어요. 이때 AI가 만들어 준 문장을 곧바로 사실로 취급하기보다, 사용자가 남긴 일정과 기록을 바탕으로 확인하는 과정이 필요해요. 아래 데모 화면은 실제 배포된 UI지만, 안에 보이는 일정과 날씨, 주가 등은 샘플 데이터예요.

Signed-in users choose interests and settings during onboarding. Calendar and task information depends on the Google permissions they connect. The dashboard separates the briefing, calendar, weather, and interest-based information into widgets. Selecting a date opens that day's events and records, while settings control which widgets appear and where they sit.

Notes and answers to daily questions feed into the diary workflow. Users can review and edit the AI-generated result. That output still needs to be checked against the events and records supplied by the user. The demo below shows the actual deployed interface, but its schedules, weather, market figures, and other content are sample data.

화면 뒤에서 데이터가 오가는 방식How data reaches the screen

화면은 React와 TypeScript로 만들고 Vite로 빌드해요. 데이터와 설정은 Zustand 저장소에서 분야별로 관리해요. 위젯은 그 상태를 읽어서 화면에 보여주고, 서비스 계층이 외부 호출과 응답 정리를 맡아요. 로그인과 사용자 데이터 저장은 Supabase Auth와 Postgres를 사용하고, 데이터베이스에서는 Row-Level Security로 사용자별 접근을 구분해요.

외부 AI나 검색처럼 비밀키가 필요한 호출은 Supabase Edge Functions에서 처리해요. 예를 들어 Smart Widget의 검색 요청은 브라우저의 서비스 코드에서 Edge Function으로 가고, 서버가 외부 검색 API를 호출한 뒤 결과를 돌려줘요. 브라우저에서 직접 쓰는 Google Maps 위치 자동완성 키는 이 흐름의 예외예요. 그래서 이 프로젝트를 설명할 때 모든 키와 API가 서버에만 있다고 묶어서 말하지 않아요.

현재 구조에는 수업이 끝난 뒤의 개선도 들어 있어요. 이 페이지는 지금 저장소에서 확인할 수 있는 동작을 설명하되, 당시 3인 팀으로 만든 부분과 이후에 제가 보완한 부분을 구분해서 적었어요.

The interface uses React and TypeScript, built with Vite. Domain-specific Zustand stores hold data and settings, widgets render that state, and a service layer handles requests and normalizes responses. Supabase Auth handles sign-in, while Postgres stores user data with Row-Level Security separating access by user.

Calls that need private AI or search API credentials go through Supabase Edge Functions. For example, a Smart Widget search travels from the browser service layer to an Edge Function, which calls the external search API and returns the result. Google Maps location autocomplete uses a browser key and is an exception to that path. It would be inaccurate to say every API call and key stays on the server.

The current repository also includes work done after the course. This page describes behavior visible in the current code, while keeping the original team project and my later improvements separate.

관심 키워드에서 위젯을 만드는 과정Turning an interest into a Smart Widget

Smart Widget은 제가 맡은 주요 기능이에요. 사용자가 키워드를 추가하면 카테고리를 분류하고, 그 주제에 맞는 검색 구성을 만들어요. 현재 코드는 주제에 따라 기본 정보, 최신 기사, 영상이나 후기처럼 다른 종류의 정보를 찾도록 나누고, Tavily 검색 결과를 정리해 카드로 보여줘요. 단순히 키워드를 AI에 한 번 보내고 나온 문장을 붙여 넣는 구조는 아니에요.

검색어가 제목에 들어 있는지, 언어가 맞는지, 중복된 URL인지 등을 확인해 결과를 추려요. 사람이름과 제품, 여행 같은 키워드가 모두 같은 방식으로 검색되면 결과가 어긋나기 쉬워서 주제별 규칙을 나눴어요. 영상 구역은 YouTube, 후기 구역은 블로그처럼 출처 종류도 구분해요. 자동으로 잡힌 카테고리가 맞지 않으면 사용자가 직접 바꾸고 키워드도 수정할 수 있어요.

언어 전환은 화면의 제목만 번역하는 문제가 아니었어요. 한국어에서 얻은 검색 결과를 영어 위젯에 그대로 재사용하지 않도록 키워드와 언어를 함께 캐시 키로 써요. 언어가 바뀌면 해당 언어의 데이터를 다시 불러오고, 결과가 없거나 가져오기에 실패한 경우도 위젯 안에서 보여주도록 했어요. 검색과 AI 요약에는 여전히 부정확한 내용이 들어올 수 있어서 원문 링크를 함께 확인할 수 있게 했어요.

Smart Widget was one of my main contributions. When someone adds a keyword, the app classifies it and plans searches suited to the topic. The current implementation looks for different kinds of material, such as basic information, recent articles, videos, and reviews, then turns Tavily search results into cards. It is more than a single prompt followed by a block of generated text.

The pipeline checks relevance in titles, language, and duplicate URLs before showing results. A person's name, a product, and a travel topic don't all need the same search, so the rules vary by category. Source types are also separated, such as YouTube for video sections and blogs for reviews. Users can override a category when the automatic choice is wrong and edit the keyword itself.

Language switching involved the data as well as the labels. Cache keys include both keyword and language so an English widget doesn't simply reuse results collected in Korean. Switching languages reloads the matching data, and widgets handle empty or failed searches. Search results and AI summaries can still be inaccurate, so the interface keeps the original links available.

API가 얽힐 때 먼저 안정시킨 것들Making the integrations behave together

여러 기능이 따로 동작해도 하나의 대시보드에 연결하면 다른 문제가 생겼어요. 로그인 직후의 데이터 로딩, Google 토큰 만료, 언어 전환과 캐시가 서로 영향을 줬어요. 막힐 때는 새 기능을 계속 붙이기보다 이미 있는 기능이 어떤 순서로 실행되고 어디서 실패하는지부터 확인했어요. API 활용 사례와 AI의 도움도 받으면서 원인을 좁히고, 안정화한 뒤 다음 기능으로 넘어갔어요.

현재 코드에는 캐시를 먼저 확인한 뒤 필요한 데이터를 갱신하는 흐름이 있어요. API 캐시는 기본 6시간 유효 기간을 두고, 데이터 종류와 언어, 관심사에 따라 키를 나눠요. 실패한 호출은 오류 상태와 대체 데이터를 구분해 다뤄요. 이 설계가 모든 최신성 문제를 없애는 것은 아니어서, 위젯의 마지막 갱신 시각과 새로고침 동작도 함께 살펴봐야 해요. 로딩 시간이 몇 퍼센트 줄었다는 식의 효과는 별도로 측정하지 않았어요.

Features that worked separately could still fail when connected in one dashboard. Initial loading after sign-in, Google token expiry, language changes, and caching affected each other. When we got stuck, I focused on the sequence of existing behavior and the point of failure before adding another feature. I used API examples and AI assistance to narrow down the cause, stabilized what was there, and then moved on.

The current code checks caches before refreshing data. API cache entries generally use a six-hour lifetime, with keys separated by data type, language, and interests. Failed calls are tracked with an error state and fallback data. That doesn't remove every freshness issue, so refresh behavior and the last-updated display still matter. I haven't measured a percentage improvement in loading time.

개인정보가 모이는 서비스에서 정한 경계Deciding where personal data and credentials belong

일정과 일기, 건강 정보가 한 서비스에 모이기 때문에 기능 연결만큼 저장과 전송 경로도 중요했어요. 외부 AI API의 비밀키는 개발 초기부터 서버 함수에서 처리하도록 설계했어요. Google 로그인에서는 장기 갱신 토큰인 provider_refresh_token을 브라우저 저장소에 남기지 않도록 했어요. 현재 저장 어댑터가 제외하는 것은 이 갱신 토큰이고, 짧게 만료되는 액세스 토큰까지 모두 저장하지 않는 구조는 아니에요.

팀원이 만든 부분도 연결과 보안 관점에서 다시 읽고 확인했어요. 외부 내용을 표시할 때 스크립트 실행 위험을 검토해 달라고 요청하고 함께 살폈어요. HTML 정제를 처음 구현한 것은 팀원이어서, 그 작업을 제 단독 구현으로 소개하지는 않아요. 학기가 끝난 뒤에는 외부 링크를 http와 https로 제한하고 서버의 사용자 확인과 입력 처리를 보완했어요.

일기 암호화도 학기 후인 2026년 10월에 추가한 선택 기능이에요. 현재 코드는 비밀번호에서 PBKDF2-SHA256으로 키를 만들고 AES-GCM으로 일기 텍스트를 암호화해요. 서버가 복호화 키를 갖지 않으므로 암호를 잊으면 복구할 수 없어요. 이 기능은 일기 저장을 보호하는 범위이고, AI 일기 생성에 선택한 내용을 외부 AI로 보내 처리하는 흐름까지 없애 주는 것은 아니에요.

Schedules, diary entries, and health information make storage and transmission choices part of the product. I designed external AI API secrets to be handled by server functions from the start. For Google sign-in, I excluded the long-lived provider_refresh_token from browser persistence. The current storage adapter removes that refresh token; it does not remove every short-lived access token as well.

I also reviewed teammates' work for integration and security issues. I asked for a review of script-execution risks in external content and checked the behavior with the team. A teammate implemented the original HTML sanitization, so I don't present that as my own implementation. After the course, I restricted external links to HTTP and HTTPS and improved server-side user checks and input handling.

Optional diary encryption was added after the course, in October 2026. The current implementation derives a key from a password using PBKDF2-SHA256 and encrypts diary text with AES-GCM. The server does not hold the decryption key, so a lost password cannot be recovered. This protects stored diary content; it does not mean that content selected for AI diary generation never reaches an external AI service.

제가 맡은 일과 함께 만든 부분My part in a three-person project

아이디어를 제안하고 초기 골격을 만든 뒤, 백엔드 설정과 인증, Google API 연결, 저장 방식, Smart Widget을 중심으로 작업했어요. 기능은 팀원들과 논의하며 정했고, 구현 뒤에는 만든 이유와 동작을 함께 확인했어요. 화면과 기능을 모두 혼자 만든 프로젝트는 아니에요. 팀 공동 작업 안에서 제가 담당한 부분과 검토한 부분을 구분해서 남겨두려 했어요.

의견이 다르거나 제가 아쉽게 느낀 부분도 있었어요. 그럴 때는 결과물을 보며 팀원이 왜 그렇게 만들었는지 듣고, 어떤 데이터를 다루고 어떤 동작이 필요한지 이야기하면서 조정했어요. 이 프로젝트에서 오래 남은 경험은 API를 연결한 일뿐 아니라, 기능이 끝났다고 느끼는 시점과 실제로 함께 동작하는 시점 사이를 점검한 일이에요.

I proposed the idea and built the initial scaffold, then focused on backend setup, authentication, Google API integration, storage decisions, and Smart Widget. We discussed features as a team and reviewed how they worked and why they were built that way. I did not build the entire interface and every feature alone. I keep my implementation work separate from the parts I reviewed or developed with others.

We didn't always see the result in the same way. When I still had concerns, I tried to understand a teammate's reasoning and discuss the data and behavior the feature needed to support. What stayed with me was the work between a feature appearing finished and the whole application actually working together.

직접 볼 수 있는 것과 아직 다른 것What the demo can show

배포된 사이트의 Explore without signing in으로 들어가면 개인 Google 계정을 연결하지 않고도 대시보드 구성을 볼 수 있어요. 실제 위젯 UI에 샘플 데이터를 넣는 방식이고, 게스트 상태는 메모리에서만 유지해요. 게스트 모드에서는 외부 API 호출과 저장 경로를 건너뛰므로 화면에서 바꾼 내용이 실제 사용자 데이터에 저장되지 않아요. 새로고침하면 로그인 화면으로 돌아가요.

이 데모로 확인할 수 있는 것은 화면 구성과 기본 상호작용이에요. 실제 Google 권한 연결, 토큰 갱신, 개인 기록 저장이 모두 검증됐다는 의미는 아니에요. 코드와 배포 화면을 함께 공개해 어떤 구조로 만들었는지 볼 수 있게 했고, 현재 저장소에는 수업 이후의 후속 작업도 포함돼 있어요.

The deployed app has an Explore without signing in option, so you can inspect the dashboard without connecting a personal Google account. It uses the real widget interface with sample data, and guest state stays in memory. Guest mode skips external API and persistence paths, so changes don't reach a real user's stored data. Reloading returns to the sign-in screen.

The demo shows the layout and basic interactions. It is not proof that Google permissions, token refresh, and personal-data storage all work in every environment. The code and deployed interface make the implementation inspectable, and the current repository includes follow-up work completed after the class.
