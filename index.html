Zero Trust Architecture ↗

서비스가 요청을 허용하거나 거부하는 기준을 직접 구성하고 검증한 학점 연구입니다. 서비스 신원과 권한을 확인하는 환경을 만들고, 정상 요청과 차단할 요청을 나누어 테스트했습니다.

An independent-study project on how services decide which requests to allow. Built identity and authorization controls, then tested both legitimate requests and requests that should be denied.

KubernetesIstio / EnvoyOPAKeycloak

5개 위협 범주, 18개 허용/거부 검증5 scenario categories, 18 allow/deny checks

자세히 보기More details접기Show less: Zero Trust Architecture

화이트해커 교육에서 Zero Trust를 접한 뒤, 실제 요청이 어떤 기준으로 허용되고 거부되는지 확인해 보고 싶어 교수님께 연구를 제안했습니다. Windows의 WSL 환경에 Kubernetes 샌드박스를 만들고 Istio/Envoy, Keycloak, OPA를 연결했습니다. 매주 구현한 내용과 판단을 설명하고 피드백을 받아 다음 실험에 반영했습니다.

처음에는 가능한 위협을 넓게 다루려 했지만, 그대로는 연구 범위를 정하기 어려웠습니다. 다섯 위협 범주로 좁힌 뒤 정상 요청과 거부되어야 할 요청을 구분해 18개 테스트를 직접 설계하고 실행했습니다. 각 요청이 왜 통과하거나 막혔는지 로그로 확인했습니다.

개념으로 배운 원칙을 실제 시스템에 옮기려면 신뢰할 구성 요소와 검증할 범위를 구체적으로 정해야 했습니다. 아래 자료는 학기 프로젝트에서 확인한 서비스 연결과 테스트 결과입니다.

After encountering Zero Trust in a white-hat security course, I proposed an independent study to my professor to see how it works on real requests. I built a Kubernetes sandbox on Windows/WSL and connected Istio/Envoy, Keycloak, and OPA. Each week, I explained my implementation and decisions, then used the feedback to plan the next experiment.

I initially tried to cover a broad range of threats, which made the scope difficult to finish. I narrowed it to five categories and designed and ran 18 tests covering requests that should pass and requests that should be denied. Logs helped me check why each request received its result.

Turning the principle into a working system required concrete decisions about which components to trust and what to verify. The materials below show the service connections and validation results from the original course project.

I proposed a dashboard that brings everyday information from separate services into one screen, then built it with two teammates. Beyond implementing individual features, we needed Google authentication, external APIs, and stored data to work together in the interface. My contributions included the initial scaffold, backend, Google API integration, and Smart Widget.

When problems emerged between APIs, I focused on stabilizing existing features before moving on to the next one. I also reviewed teammates' work for integration and security issues.

Because the app collects schedules and diary entries, I looked at where information is stored and sent. External AI API secrets were handled by server functions from the start, and Google refresh tokens were excluded from browser storage. Traffic Digital Twin

CCTV 영상 속 차량을 탐지하고, 위치와 속도를 지도에 연결하는 2인 프로젝트입니다. 영상 처리와 백엔드 연결을 맡았고, 카메라별 차이와 노트북 GPU의 처리 병목을 해결하는 데 집중했습니다.

A two-person project connecting vehicle detection in CCTV footage to positions and speeds on a map. I worked on video processing and backend integration, with a focus on camera differences and laptop GPU bottlenecks.

Computer visionFastAPITensorRT

자세히 보기More details접기Show less: Traffic Digital Twin

CCTV 영상에 차량 탐지 모델을 연결해 교통 상황을 지도에서 볼 수 있게 하자는 아이디어에서 시작했습니다. 두 사람 모두 컴퓨터 비전이 처음이라 필요한 원리를 공부하며 구현 방향을 정했습니다. 저는 알고리즘과 데이터 준비, OpenCV 영상 처리, FastAPI 연결을 맡았고 중간 결과를 함께 보며 접근을 보완했습니다.

카메라마다 촬영 각도와 위치가 다르고 움직임도 있어, 한 영상에 맞춘 방식이 다른 영상에서는 그대로 통하지 않았습니다. 변수를 하나씩 확인하며 위치와 속도 추정 방식을 다듬었습니다. 노트북 GPU의 추론이 입력을 따라가지 못했을 때는 TensorRT 사용을 제안하고 모델을 엔진으로 변환했습니다.

후속 보고서에서는 같은 조건으로 처리 시간을 비교했습니다. 탐지/추적 단계의 평균 지연은 PyTorch CUDA 8.4ms, TensorRT FP16 6.7ms였습니다. 아래에 측정 조건과 실제 화면, 초기 Showcase 포스터를 함께 정리했습니다. 화면과 포스터, 벤치마크는 각각의 버전과 조건을 구분해 보아야 합니다.

The project began with an idea to connect CCTV vehicle detection to a map of traffic conditions. Computer vision was new to both of us, so we studied the relevant concepts while deciding how to build it. I worked on algorithms, data preparation, OpenCV processing, and FastAPI integration, and we reviewed intermediate results together.

Camera angles, positions, and movement varied, so an approach that worked for one video did not transfer directly to another. I checked the variables one at a time to refine position and speed estimation. When inference on the laptop GPU could not keep up with the input, I proposed TensorRT and converted the model into an engine.

A later report compared processing time under the same conditions: mean detection/tracking latency was 8.4ms with PyTorch CUDA and 6.7ms with TensorRT FP16. 거절 행동에 미치는 영향How model weights and deployment prompts interact in refusal behavior

같은 모델이라도 배포 프롬프트가 달라지면 거절 행동이 어떻게 바뀌는지 실험한 단독 연구입니다. 가중치와 프롬프트를 함께 비교했고, 예상과 다른 결과를 추적하며 평가 도구의 오류도 확인했습니다.

A solo study of how deployment prompts change refusal behavior for the same model. Compared weights and prompts together, and traced unexpected results to errors in the evaluation tools.

자세히 보기More details접기Show less: LLM safety research

AI Summer Camp 이후 LLM 보안에 관심이 생겼고, 떠올린 생각이 실제 실험에서도 성립하는지 확인해 보고 싶었습니다. 익숙하지 않은 개념은 AI의 도움을 받아 공부하고 Kaggle에서 직접 실험을 돌렸습니다. 혼자 해결되지 않는 부분은 동료 연구자에게 조언을 구하면서 질문을 구체화했습니다.

연구에서는 모델 가중치와 평가 요청을 유지한 채 배포 프롬프트를 바꾸어 거절 행동을 비교했습니다. 모델 자체를 평가한 결과가 실제 사용 조건에서도 유지되는지 살펴보려는 실험이었습니다. AI는 코드 구현과 분석, 글 정리에도 활용했고 실험 방향과 결과 해석은 직접 판단했습니다.

결과가 이상하게 나온 이유를 따라가다 거절 문장의 따옴표 하나를 탐지기가 놓치고 있다는 사실을 발견했습니다. 응답 길이를 다루는 규칙도 최대 길이 도달과 자발적 종료를 혼동하고 있었습니다. 측정 기준을 고친 뒤 다시 분석해 주요 결과가 유지되는지 확인했고, 한 모델 계열과 정해진 실험 조건에서 관찰한 사례로 정리했습니다.

After an AI Summer Camp, I became interested in LLM security and wanted to test whether an idea would hold up in an experiment. I used AI to study unfamiliar concepts and ran experiments on Kaggle. When I could not resolve something alone, I asked fellow researchers for advice and refined the question.

I kept model weights and evaluation requests fixed while changing the deployment prompt to compare refusal behavior. The aim was to see whether an assessment of the model would hold across different usage conditions. I also used AI for implementation, analysis, and writing, while making the decisions about experiment direction and interpretation myself.

Following up on unexpected results, I found that the refusal detector missed a typographic apostrophe in a refusal phrase. A length rule also confused reaching the generation limit with stopping voluntarily. I corrected the measurement rules and reanalyzed the results to check whether the main findings held, keeping the conclusions within one model family and the tested conditions.
