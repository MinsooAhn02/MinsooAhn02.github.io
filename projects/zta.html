개념을 직접 확인해 보고 싶었어요From a concept to a working experiment

화이트해커 교육에서 Zero Trust를 접했어요. 내부 네트워크에서 온 요청도 그대로 믿지 않는다는 원칙이 흥미로웠는데, 설명을 읽는 것과 실제로 요청을 막거나 통과시키는 것은 다른 일 같았어요. 교수님께 연락해 Spring 2026 CSE 487 학점 연구로 이어갔어요.

지도교수는 Tony Mione 교수님이었어요. 매주 제가 구성한 것과 그렇게 정한 이유를 설명하고 피드백을 받았어요. 막혔을 때는 먼저 제 생각을 정리하고 자료와 AI로 찾아본 뒤, 남은 질문을 교수님께 가져가는 방식으로 진행했어요.

이 페이지의 첫 번째 기준은 학기 중에 만든 로컬 실험과 18개 테스트예요. 학기 후 확장한 v2도 마지막에 따로 소개해요. 두 버전의 기능이나 결과를 합쳐서 학기 프로젝트의 성과로 보지는 않아요.

I encountered Zero Trust in a white-hat security course. The idea of not automatically trusting an internal request interested me, but reading the principle felt different from making a request actually pass or fail. I contacted a professor and developed the question into a supervised CSE 487 independent study in Spring 2026.

Tony Mione supervised the project. Each week, I explained what I had configured and why, then used his feedback to plan the next step. When I got stuck, I first worked through my own ideas, consulted documentation and AI, and brought the remaining questions to him.

The main reference here is the original local experiment and its 18 tests. I describe the post-course v2 separately at the end. Its controls and results belong to a later version, rather than being added to what the original course project demonstrated.

요청이 지나가는 길을 나눴어요Following a request through the system

Windows에 WSL을 설치하고 Linux 안에서 Kubernetes 샌드박스를 만들었어요. 작은 Flask frontend와 backend 사이에 Istio의 Envoy 프록시를 두고, Keycloak은 사용자 토큰 발급에, OPA는 접근 정책 판단에 연결했어요. 이 환경은 서비스를 운영하기 위한 구축이 아니라 통제가 어떻게 작동하는지 확인하기 위한 실험이었어요.

사용자 요청에서는 토큰이 유효한지와 그 사용자에게 해당 경로를 사용할 권한이 있는지를 구분했어요. Keycloak의 공개 키로 JWT 서명을 확인하는 일과, admin이나 viewer가 어떤 요청을 할 수 있는지 정하는 일은 서로 다른 단계예요. OPA에서는 역할뿐 아니라 HTTP 메서드와 경로도 판단에 사용했어요.

서비스끼리의 연결에는 또 다른 신원이 필요했어요. frontend에서 backend로 가는 연결은 mTLS와 서비스 계정 신원으로 제한했어요. 따라서 사용자 토큰 검사, 요청 권한 판단, 서비스 간 신원 확인을 하나의 검사라고 부르지 않고 각각 살펴봤어요.

I used Windows with WSL to build a Linux-based Kubernetes sandbox. A small Flask frontend and backend were connected through Istio's Envoy proxies. Keycloak issued user tokens, while OPA evaluated authorization rules. This was an experiment for observing controls, rather than a production service deployment.

For user requests, I separated token validity from permission to use a route. Verifying a JWT signature against Keycloak's public keys is different from deciding what an admin or viewer may do. The authorization rules considered the role together with the HTTP method and path.

Service-to-service traffic needed another kind of identity. The frontend-to-backend connection was restricted using mTLS and service-account identity. I treated user-token verification, request authorization, and workload authentication as separate checks, because each addresses a different part of the path.

모든 위협을 다룰 수는 없었어요Choosing a scope I could actually test

처음에는 생각나는 공격 경로를 넓게 다루려고 했어요. 하지만 위협을 계속 추가하면 구현도 검증도 끝내기 어렵겠더라고요. 결국 서비스 간 이동, JWT 위조와 변조, 요청 맥락, JWT 역할 권한, 장치 상태의 다섯 범주로 범위를 정했어요.

각 범주에서 차단할 요청만 만들지는 않았어요. 정상 사용자가 읽을 수 있어야 할 데이터와 관리자가 접근할 수 있어야 할 경로도 같이 확인했어요. 전부 막힌다는 사실만으로는 정책이 의도대로 동작하는지 알 수 없기 때문이에요.

제가 직접 18개 테스트를 설계하고 실행했고, 최종 로그에서는 모두 예상한 결과와 맞았어요. 여기서 18은 막은 공격 개수가 아니라 허용과 거부를 함께 확인한 시나리오 수예요. 다섯 범주도 실제 환경의 모든 위협을 포괄한다는 뜻은 아니에요.

I initially tried to cover a broad set of possible attack paths. As the list grew, it became difficult to finish either the implementation or its validation. I narrowed the study to five categories: lateral movement, JWT forgery and tampering, request context, JWT role authorization, and device-posture gating.

I included legitimate requests alongside requests that should be blocked. A viewer still needed to read permitted data, and an admin still needed access to the appropriate routes. If everything failed, that would not tell me whether the intended authorization policy was working.

I designed and ran 18 tests, and the final log matched the expected outcome for every case. Eighteen is the number of allow-and-deny checks, not the number of attacks blocked. The five categories define the study's scope; they do not claim to cover every threat in a real deployment.

같은 경로도 신원에 따라 달라져요Concrete requests and their observed outcomes

예를 들어 D-1에서는 admin JWT로 GET /api/admin을 보내 200을 받았어요. D-3에서는 같은 관리자 경로에 viewer JWT를 보내 403을 확인했고, D-2의 viewer GET /api/data는 200으로 통과했어요. 경로만 보는 대신 요청자의 권한과 함께 판단하는지 확인한 묶음이에요.

B-2에서는 정상 JWT의 payload를 바꾸고 기존 서명을 그대로 재사용해 401이 나오는지 확인했어요. B-4의 Keycloak 발급 정상 토큰은 200으로 통과했어요. 토큰처럼 생긴 문자열이 있다는 사실과 서명이 유효하다는 사실을 구분해서 본 테스트예요.

서비스 간 경로에서는 sidecar가 없는 rogue pod와 허용되지 않은 서비스 계정, backend pod IP로 직접 접근하는 경우를 따로 확인했어요. 로그에 남은 응답은 각각 403, 403, 503이었어요. 마지막 503을 정상적인 애플리케이션 권한 거부와 같은 의미로 읽지는 않고, 해당 실험에서 연결이 차단된 결과로 기록했어요.

For example, D-1 sent GET /api/admin with an admin JWT and received 200. D-3 used a viewer JWT on the same admin route and received 403, while D-2 allowed the viewer to read /api/data with 200. Together, these checks examined the route and the caller's permissions rather than the route alone.

B-2 modified a real JWT's payload while reusing its original signature and received 401. B-4 used a valid Keycloak-issued token and received 200. This distinguished the presence of a token-shaped string from a token whose signature could actually be verified.

For the service path, I separately tested a rogue pod without a sidecar, an unauthorized service account, and a direct call to the backend pod IP. The recorded statuses were 403, 403, and 503. I keep that last result as an observed blocked connection in this setup, rather than presenting every failure status as the same application-level authorization decision.

실험을 위해 남긴 신뢰도 적었어요The trust assumptions behind the demo

원본 프로젝트에는 비교를 위해 role 헤더를 사용하는 데모 규칙이 있었어요. A-NS-2처럼 role:admin 헤더만 붙여 통과하는 테스트가 있어, 원본 전체가 모든 경로에서 JWT를 강제했다고 말하면 틀려요. 보고서에서는 이 규칙이 demo_mode에 묶여 있고, 끄면 서명된 JWT 기반 규칙이 남는다고 구분했어요.

장치 방화벽 상태도 실제 기기를 측정한 값은 아니었어요. 원본 E-1과 E-2는 같은 admin JWT에 방화벽 상태 헤더를 다르게 넣어 200과 403을 비교한 모의 실험이에요. 장치 상태를 정책에 넣을 수 있다는 동작을 본 것이지, 단말 보안 상태를 검증하는 제품을 만든 것은 아니에요.

OPA로 가는 ext-authz 통신은 sidecar 바깥의 평문 gRPC였어요. OPA에도 같은 인가 필터가 걸리면 인가 요청을 다시 인가하는 순환이 생길 수 있어 메쉬 밖에 뒀어요. 원본 환경에서는 NetworkPolicy manifest가 있어도 CNI 수준의 집행을 전제로 삼을 수 없었고, 이 구간은 클러스터 격리에 기대는 한계가 있었어요.

The original project included header-based demo rules for comparison. A case such as A-NS-2 allowed a request carrying role:admin, so it would be inaccurate to say the original system required a JWT on every path. The report separates these demo_mode rules from the signed-JWT rules that remain when that mode is disabled.

Device posture was also simulated, rather than measured from a real endpoint. E-1 and E-2 used the same admin JWT with different firewall-state headers and observed 200 versus 403. They demonstrated how a posture input could affect a rule, not an endpoint-attestation or device-security product.

The ext-authz connection to OPA used plaintext gRPC outside the sidecar mesh. Applying the same authorization filter to OPA could recursively authorize authorization requests, so OPA was kept outside that path. Although a NetworkPolicy manifest existed, the original sandbox did not establish CNI-level enforcement; this channel relied on cluster isolation.

통제를 켜는 데 드는 비용도 봤어요Measuring the cost of the full control stack

정책을 추가했을 때 정상 요청의 처리 시간이 얼마나 달라지는지도 확인했어요. 원본 측정은 Istio sidecar는 있지만 해당 인증과 인가 정책은 적용하지 않은 기준선과, mTLS와 OPA, Envoy 통제를 적용한 구성을 비교했어요. Fortio로 연결 하나에서 요청 200개를 보낸 로컬 실험이에요.

원시 로그의 평균 지연은 5.332ms에서 6.859ms로 늘었고, QPS는 187.5에서 145.7로 줄었어요. 반올림하면 평균 지연 +1.53ms, QPS -22.3%예요. 특정 정책 함수 하나의 비용이 아니라 구성 전체의 차이로 읽어야 해요.

연결 하나에서 요청 200개를 한 번 측정한 결과라 반복 실행의 변동이나 높은 동시성에서의 최대 처리량은 알 수 없어요. 차단 요청은 앱에 도달하기 전에 끝나므로 정상 요청보다 짧게 걸렸다는 이유로 성능 개선이라고 부르지도 않아요. 이 결과는 보호 수준과 처리 비용을 함께 보는 출발점이었어요.

I also examined what the controls cost for legitimate requests. The original measurement compared a sidecar-present baseline without the relevant authentication and authorization policies against the full mTLS, OPA, and Envoy control setup. Fortio sent 200 requests over a single persistent connection in the local environment.

The raw logs show mean latency rising from 5.332ms to 6.859ms and QPS falling from 187.5 to 145.7. Rounded, that is +1.53ms in mean latency and -22.3% QPS. It describes the difference between complete configurations, rather than the isolated cost of one policy function.

A single 200-request run does not establish run-to-run variability or maximum throughput at high concurrency. A denied request also ends before the application handles it, so its shorter latency is not evidence of an application performance improvement. The result was a starting point for considering protection and processing cost together.

학기 후에는 신뢰 경계를 더 엄격하게 바꿨어요A separate post-course hardening version

학기 후 zta-v2-hardening에서는 원본 실험을 보존하고 별도 환경에서 확장했어요. frontend와 backend 양쪽의 JWT와 OPA 검사, backend가 frontend 서비스 신원을 요구하는 경계, 정확한 메서드와 경로 검사처럼 원본에서 느슨했던 부분을 더 분명하게 만들었어요.

role이나 X-Device-Firewall 같은 요청 헤더를 권한 근거로 쓰는 대신, 서명된 사용자 토큰과 별도의 상태 토큰을 함께 확인해요. 상태 토큰도 실제 기기를 관측한 결과는 아니라 서명된 테스트 주장이라는 한계는 그대로 남아요. 사용자 토큰과 같은 사용자인지, 유효 시간이 맞는지도 확인하도록 구성했어요.

v2 기록의 34개 coverage는 기능 검사 33개와 성능 실험 S32를 포함한 수예요. 원본 18개와 합산하지 않아요. 성능도 고정 8 QPS, 동시성 1과 4, 각 30초씩 3회라는 다른 조건이라 원본 수치와 직접 비교하지 않아요. 결과 문서에 기록된 fingerprint의 검증이며, 이후 UI 변경까지 같은 전체 검증을 다시 했다는 뜻도 아니에요.

After the course, I preserved the original experiment and extended it in a separate zta-v2-hardening environment. The later version adds JWT and OPA checks at both frontend and backend, requires the frontend workload identity at the backend, and makes method-and-path matching explicit.

Instead of trusting role or X-Device-Firewall headers, the later version checks a signed user token together with a separate posture token. That posture token is still a signed test assertion, not a measurement of a physical device. The checks also bind it to the same user and enforce its time limits.

The v2 record reports 34 coverage items: 33 functional checks plus performance experiment S32. I do not add them to the original 18. Its performance runs use a fixed 8 QPS, concurrency 1 and 4, and three 30-second repetitions, so they are not a direct comparison with the original numbers. The recorded validation applies to its source fingerprint, not automatically to later UI changes.

제가 가져간 것은 테스트를 정하는 방법이에요What I took from the project

학기 연구에서 제가 맡은 일은 실험 환경을 구성하고, 다룰 위협과 예상 응답을 정하고, 테스트를 직접 설계해 실행하는 것이었어요. 교수님과 매주 검토하면서 처음의 넓은 생각을 실제로 확인할 수 있는 요청 단위로 줄여갔어요. 학과 Showcase에서는 이 작업을 구두로 발표했어요.

중요했던 것은 통제를 많이 켰다는 설명보다 어느 요청에서 어떤 계층이 판단했는지 보여주는 일이었어요. JWT 서명 오류와 역할 부족, 서비스 신원 불일치는 모두 요청을 막을 수 있지만 같은 원인은 아니에요. 허용되는 대조 요청과 로그를 함께 남겨야 그 차이를 설명할 수 있었어요.

실험을 넓힌다면 실제 장치 상태를 어떻게 신뢰할지와 환경을 바꿨을 때도 결과가 이어지는지를 더 확인해야 해요. 지금의 자료가 보여주는 것은 정해진 로컬 환경에서 관찰한 동작과 비용이에요. 운영 환경 적용이나 모든 공격의 차단으로 범위를 넓히지는 않아요.

My work in the course study was configuring the environment, selecting threats and expected responses, and designing and running the tests. Weekly discussions with my professor helped turn a broad idea into requests I could actually check. I presented the work orally at the department Showcase.

The useful part was showing which layer made a decision for a particular request. An invalid JWT signature, insufficient role, and wrong workload identity can all block traffic, but they are different causes. Keeping legitimate control requests and logs alongside failures made those differences easier to explain.

Extending this work would require a credible source of real device posture and further checks across different environments. The existing material demonstrates behavior and cost under defined local conditions. It does not establish production readiness or protection against every attack.
