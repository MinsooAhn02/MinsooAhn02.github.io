Zero Trust Architecture ↗

Zero Trust를 작은 실험 환경에 옮겨봤어요. 누가 보낸 요청인지, 어떤 권한이 있는지 확인하고, 통과해야 할 요청과 막혀야 할 요청을 나눠 테스트했어요.

I wanted to see how Zero Trust works with real service requests. I set up identity and access checks between services, then tested which requests got through and which were blocked.

KubernetesIstio / EnvoyOPAKeycloak

5개 위협 범주, 18개 허용/거부 검증5 scenario categories, 18 allow/deny checks

자세히 보기More details접기Show less: Zero Trust Architecture

화이트해커 교육에서 Zero Trust를 처음 접했어요. 개념으로 배운 내용을 직접 확인해 보고 싶어서 교수님께 연구를 제안했어요. Windows의 WSL에 Kubernetes 실험 환경을 만들고 Istio/Envoy, Keycloak, OPA를 연결했어요. 매주 만든 것과 그렇게 정한 이유를 설명하고, 교수님 의견을 받아 다음 실험을 이어갔어요.

처음에는 떠오르는 위협을 넓게 다루려 했는데, 그렇게는 끝내기 어렵겠더라고요. 다섯 범주로 범위를 좁히고, 정상 요청과 거부해야 할 요청을 나눠 테스트 18개를 직접 만들고 실행했어요. 요청마다 예상한 응답이 나오는지, 왜 통과하거나 막혔는지 로그를 보며 확인했어요.

직접 만들어 보니 어디까지 확인할지, 어떤 구성 요소는 믿고 사용할지를 정해야 했어요. '아무것도 믿지 않는다'는 말만으로 구현이 끝나지는 않더라고요. 아래에는 학기 중에 만든 서비스 연결 구조와 테스트 결과를 모아뒀어요.

I first came across Zero Trust in a white-hat security course and asked my professor if I could study it through a working system. I set up a Kubernetes sandbox on Windows/WSL and connected Istio/Envoy, Keycloak, and OPA. Each week, I walked through what I'd built and why, then used the feedback to decide what to try next.

At first, I tried to cover too many threats at once. I narrowed the project to five categories and wrote 18 tests, including requests that should pass and requests that should be denied. I checked the logs to see why each request got through or was blocked.

Once I started building it, I had to decide exactly which components the system would trust and what each check would cover. Below are the service connections and test results from that semester's project.

A dashboard that brings schedules, diary entries, weather, and other daily information into one place. I pitched the idea and built it with two teammates, mainly working on the backend and connecting external services.

여러 서비스에 흩어진 일상 정보를 한곳에서 보면 어떨까 하는 생각으로 시작했어요. 팀원 두 명과 기능을 나눠 만들면서 Google 로그인과 외부 API, 저장한 정보가 화면까지 잘 이어지도록 연결했어요. 저는 프로젝트의 초기 골격과 백엔드, Google API 연동, Smart Widget을 맡았어요.

API 여러 개를 연결하다 보니 한 부분을 바꿨을 때 다른 곳에서 문제가 생기기도 했어요. 그럴 때는 이미 만든 기능부터 안정시킨 뒤 다음 기능으로 넘어갔어요. 팀원이 만든 부분도 함께 살펴보며 연결이 맞는지, 보안상 놓친 부분은 없는지 확인했고요.

일정과 일기가 쌓이는 서비스라 정보가 어디에 저장되고 전달되는지도 신경 썼어요. 외부 AI API 비밀키는 처음부터 서버 함수에서 처리하게 만들고, Google 로그인 갱신 토큰은 브라우저에 저장하지 않도록 바꿨어요. 학기가 끝난 뒤에는 일기 종단간 암호화도 추가했어요. 아래는 개인 계정 없이 볼 수 있는 실제 게스트 화면이에요.

I suggested putting the information we use throughout the day on one screen and built the dashboard with two teammates. That meant getting Google sign-in, external APIs, and saved data to work together, as well as building the individual features. I worked on the initial setup, backend, Google API connections, and Smart Widget.

When the APIs didn't work together as expected, I went back and got the existing features working before adding more. I also checked how my teammates' work connected to the rest of the app and looked for security issues.

With schedules and diary entries in the app, I also checked where that information was saved and sent. I designed it so server functions handled the secret keys for external AI APIs from the start, and kept Google refresh tokens out of browser storage. After the semester, I added end-to-end encryption for diary entries. The screenshot below shows the guest demo, without opening a personal account.

Traffic Digital Twin

CCTV 속 차량을 지도 위로 옮겨 보자는 아이디어에서 시작했어요. 팀원과 함께 만들면서 저는 영상 처리와 백엔드 연결을 맡았어요. 카메라마다 다른 조건에 맞추고, 노트북 GPU가 영상을 제때 처리하게 만드는 일이 쉽지 않았어요.

This started with an idea to put the vehicles in CCTV footage onto a map. I built it with a teammate, working on video processing and the backend, then on camera differences and inference speed on a laptop GPU.

Computer visionFastAPITensorRT

후속 실험의 탐지/추적 평균 지연: 8.4 → 6.7msA later benchmark: mean detection/tracking time went from 8.4 to 6.7 ms

자세히 보기More details접기Show less: Traffic Digital Twin

CCTV에 차량 탐지 모델을 연결하면 교통 상황을 지도에서 볼 수 있겠다고 생각했어요. 둘 다 컴퓨터 비전이 처음이라 원리를 공부하면서 만드는 방법을 찾아갔어요. 저는 알고리즘과 데이터 준비, OpenCV 영상 처리, FastAPI 연결을 맡았고, 중간 결과를 함께 보며 고쳐나갔어요.

카메라마다 각도와 위치가 다르고 화면이 움직이기도 해서, 한 영상에 맞춘 방식이 다른 영상에서는 잘 맞지 않았어요. 변수를 하나씩 확인하면서 위치와 속도를 추정하는 방식을 다듬었어요. 노트북 GPU가 들어오는 영상을 제때 처리하지 못했을 때는 TensorRT를 써보자고 제안하고 모델을 엔진으로 직접 변환했어요.

후속 실험에서는 같은 조건으로 처리 시간을 비교했어요. 탐지·추적 단계의 평균 지연은 PyTorch CUDA에서 8.4ms, TensorRT FP16에서 6.7ms였어요. 아래에는 측정 조건과 실제 화면, 초기 Showcase 포스터를 모아뒀어요. 화면과 포스터는 벤치마크와 버전·입력 영상이 달라서 각각 따로 표시했어요.

We wanted to detect vehicles in CCTV footage and show the traffic on a map. Neither of us had worked with computer vision before, so we learned what we needed as we built it. I worked on the algorithms, data preparation, OpenCV processing, and FastAPI connections. We looked at the results together as we went and adjusted our approach.

A method that worked for one video didn't necessarily work for another: the cameras had different angles, positions, and movement. I checked those differences one at a time to improve the position and speed estimates. When the laptop GPU couldn't keep up with the input, I suggested TensorRT and converted the model into an engine.

In a later report, I compared processing time under the same conditions. Mean detection/tracking time was 8.4 ms with PyTorch CUDA and 6.7 ms with TensorRT FP16. Below are the test conditions, a screenshot from the app, and our earlier Showcase poster. I've labeled the versions and inputs because they aren't all from the same experiment.

모델 가중치와 배포 프롬프트가
거절 행동에 미치는 영향The same model, different prompts: what changes in refusal behavior?

같은 모델도 배포 프롬프트가 바뀌면 거절하는 방식이 달라질까 궁금했어요. 직접 실험하면서 결과를 비교했고, 그 과정에서 평가 도구가 일부 응답을 잘못 읽는 문제도 찾았어요.

I was curious about how much a model's refusal behavior could change just by changing the prompt. I ran experiments to compare it and found that the evaluation tools were misreading some responses, too.

자세히 보기More details접기Show less: LLM safety research

AI Summer Camp 이후 LLM 보안에 관심이 생겼어요. 떠올린 생각이 실험에서도 맞을지 확인해 보고 싶어서, 익숙하지 않은 개념을 AI의 도움으로 공부하고 Kaggle에서 직접 실험을 돌렸어요. 혼자 풀리지 않는 부분은 교류하던 연구자들에게 물어보며 질문을 구체화했어요.

각 모델의 가중치와 평가 요청은 그대로 두고 배포 프롬프트를 바꿔가며 거절 행동을 비교했어요. 한 조건에서 얻은 모델 평가가 다른 사용 조건에서도 이어지는지 보고 싶었어요. 코드와 분석, 글 정리에는 AI를 활용했고, 무엇을 실험할지와 결과를 어떻게 해석할지는 직접 판단했어요.

예상과 다른 결과를 따라가다 탐지기가 거절 문장 안의 따옴표 차이를 놓친다는 걸 발견했어요. 응답 길이를 보는 규칙도 최대 길이에 도달한 경우와 모델이 스스로 끝낸 경우를 혼동하고 있었어요. 두 기준을 고친 뒤 다시 분석해 주요 결과가 유지되는지 확인했어요. 결론은 실험한 한 모델 계열과 조건 안에서 관찰한 사례로 한정했어요.

I became interested in LLM security after an AI Summer Camp and wanted to see whether an idea I had would hold up in an experiment. I used AI to learn the concepts I didn't know yet and ran the experiments myself on Kaggle. When I got stuck, I asked other researchers for advice and worked on making the question more specific.

I kept the model weights and evaluation requests the same, then changed the deployment prompt and compared refusal behavior. I wanted to see whether a result from one evaluation condition would hold under another. I used AI for code, analysis, and writing as well, while deciding the experiment's direction and interpreting the results myself.

While tracing results that didn't look right, I found that the refusal detector missed a refusal phrase because of its curly apostrophe. A rule for response length also confused hitting the generation limit with the model stopping on its own. I fixed the measurement rules and ran the analysis again to check whether the main findings still held. I kept the conclusions to the one model family and the conditions I tested.
